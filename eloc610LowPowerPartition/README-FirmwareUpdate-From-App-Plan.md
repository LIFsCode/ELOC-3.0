# Feature Plan: Firmware Updates from the ELOC Android App

## Context

ELOC devices are solar-powered bioacoustic recorders deployed high in trees in Sumatran rainforest.
Today the only way to update firmware is to physically retrieve the SD card, copy `elocupdate.bin` +
a trigger file onto it, and reboot the device — a ladder-and-hike operation. The goal is to let a field
tech update firmware from the Android app over the existing Bluetooth SPP connection: download a release
while online (in town), then stream it to the device in the field, with the device flashing it safely
and reporting the new version back.

**Architecture (agreed with user):** app downloads a hashed release → streams it over BT into the
device's existing SD staging path (`/sdcard/eloc/update/elocupdate.bin`) → device verifies SHA-256 →
device flashes at next boot using the existing (fixed-up) SD updater → app reconnects and confirms the
new version. SD staging (not direct-to-flash streaming) is deliberate: it reuses the existing boot-time
flash path, keeps the flash step atomic and offline, tolerates BT drops with zero risk, enables resume,
and keeps the manual SD-swap fallback working.

### Decisions already made by the user

- **Battery thresholds (firmware-enforced):** refuse update below **3.1 V for LiFePO₄**, **3.5 V for
  lithium (LiPo)**. Firmware auto-detects battery type (`Battery.cpp:147` — IO expander
  `hasLiIonBattery()`), so the check lives in `setFwUpdateBegin`, not the app.
- **No 4 MB-flash devices in the field** — no need for multi-layout gating; a simple
  `size ≤ target slot size` check in `setFwUpdateBegin` suffices.
- **Release channels:** `stable` default, `beta` opt-in per user profile.
- **Partition0 hardware verification** (what's actually in the other OTA slot on deployed devices) is
  **deferred — the user will check on real hardware**. This gates *field rollout*, not development.
  See "Open items" at the bottom.

### Protocol constraints (verified in code)

- BT is Classic SPP; commands are `#`-separated key/value text parsed by `CmdParser`
  (`setOptSeperator('#')`, `setOptIgnoreQuote(true)`); responses are **EOT(0x04)-terminated JSON**
  `{"id","cmd","ecode","payload"}`.
- App enforces **512-byte max per command** — a multi-MB binary cannot use the command path; a **raw
  binary receive mode** in the firmware is required (base64-over-commands would take hours).
- No WiFi stack is compiled in; BT SPP is the only app↔device channel. Realistic throughput
  30–80 KB/s → ~3 MB EI build transfers in ~1–2.5 min.
- Firmware has **two build variants**: `esp32dev` (no AI) and `esp32dev-ei` (Edge Impulse). Releases
  ship both; the device must report which it runs so the app picks the right binary.
- `sdkconfig.defaults` is the place for new ESP-IDF config (per `platformio.ini` comments).

## Phase 0 — Fix the existing SD updater (firmware only; prerequisite; independently shippable)

**Files:** `lib/FirmwareUpdate/src/FirmwareUpdate.cpp`, `.hpp`; `sdkconfig.defaults`; `src/main.cpp`.

1. **Fix confirmed bugs in `FirmwareUpdate.cpp`:**
   - `updateFirmware()` (line ~191): the `if (updatePartition != NULL) {}` block is **empty** and
     `try_update()` is called unconditionally → NULL-deref crash path when `checkIfCanUpdate()`
     returns NULL. Guard properly.
   - `fclose(f)` is called on a NULL handle when the update file doesn't exist.
   - `try_update()` ignores `esp_ota_write()` errors mid-loop, never frees `data.data` on early
     return, never calls `esp_ota_abort()` on failure.
2. **Remove the compile-date comparison** in `checkIfCanUpdate()` (fragile `strptime` on
   `esp_app_desc_t` date strings). The app/user decides *whether* to update (downgrades must be
   allowed); the device only verifies *integrity*. Replace with: image-header sanity check
   (`esp_image` magic, `esp_app_desc_t` readable via `esp_ota_get_partition_description` semantics,
   file size ≤ `esp_ota_get_next_update_partition()->size`).
3. **Add SHA-256 verification**: read expected hash from a small JSON metadata file next to the
   binary (`/sdcard/eloc/update/elocupdate.json`, written by the app in Phase 1 / by hand for the
   SD-swap path — make hash optional for the manual path, warn if absent). Use mbedtls
   (`mbedtls/sha256.h`, already in ESP-IDF).
4. **Enable rollback:** `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y` in `sdkconfig.defaults`. In
   `main.cpp`, after a successful post-boot self-test (SD mounted, config loaded, BT server started —
   i.e., late in `app_main` setup on non-timer wake), call `esp_ota_mark_app_valid_cancel_rollback()`
   when `esp_ota_get_state_partition()` reports `ESP_OTA_IMG_PENDING_VERIFY`. A crashing update then
   auto-reverts to the previous slot.
5. **Write a result file** `/sdcard/eloc/update/result.json` (`fromVersion`, `toVersion`, `outcome`,
   timestamp) before restarting, so the app can read the outcome after reconnect even if logs rotate.
   Delete the staged `.bin` on success.
6. Note in code + memory-bank: rollback protects updates *from this version onward*; the first OTA
   onto older firmware still rides the old updater.

**Verify:** bench device — SD-swap update still works; corrupt/truncated bin refused; power-pull during
flash → old slot still boots (repeat several times); deliberately-crashing image → auto-rollback.

## Phase 1 — BT transfer protocol (firmware)

**Files:** new code in `lib/FirmwareUpdate/` (transfer state machine, e.g. `FwUpdateTransfer.{hpp,cpp}`);
hooks in `lib/Commands/src/BluetoothServer.cpp` and `ElocCommands.cpp`.

### New commands (all standard EOT-JSON responses)

| Command | Behavior |
|---|---|
| `setFwUpdateBegin#meta={...}` | Meta: `size`, `sha256`, `version`, `variant`, `chunkSize` (default 4096, max 8192). Preflight: recording+AI off (`wav_writer.get_mode()==disabled`, `!ai_run_enable`), SD mounted, free space ≥ size + 1 MB, **battery ≥ 3.1 V (LiFePo) / 3.5 V (LiPo)** via `Battery::GetInstance()`, size ≤ inactive slot size. On OK: open/append staging file, reply `{"resumeOffset": N}` — N>0 only if an existing partial file matches the same `sha256` metadata (persist meta beside the partial); otherwise truncate and 0. Enter binary receive mode. |
| *(binary frames)* | `[seq:u16 LE][len:u16 LE][payload ≤ chunkSize][crc32:u32 LE]`. Firmware reads frames directly from `SerialBT` (bypassing `CmdParser` via a mode flag checked at the top of `wait_for_bt_command()`), verifies CRC + expected seq, appends to staging file, acks each frame with a short EOT-JSON (`{"seq":N,"ecode":0}` shape consistent with existing responses). Stop-and-wait: app sends next frame only after ack. RFCOMM is a reliable stream — CRC/seq is for pacing and desync detection, not retransmission. NAK (nonzero ecode) → app resyncs via `getFwUpdateStatus`. |
| `getFwUpdateStatus` | `{state: idle/receiving/staged/error, bytesReceived, expectedSize, sha256}` — drives resume + UI. |
| `setFwUpdateAbort` | Exit binary mode; optional `discard=true` deletes partial file. Firmware also self-aborts binary mode after **30 s without a frame** or on BT disconnect (partial file kept for resume). |
| `setFwUpdateApply` | Recompute SHA-256 from the staged SD file, compare to Begin meta; image-header sanity check; write `/sdcard/eloc/update/elocupdate.json` metadata + `doUpdate.txt` trigger; reply OK; `esp_restart()`. |

### Additional firmware work

- **Capability advertisement in `getStatus`:** add to the `device` object: `fwUpdateProto: 1`,
  `buildVariant: "ei"|"no-ai"` (derive from `EDGE_IMPULSE_ENABLED`), and inactive-slot size. Old apps
  ignore unknown keys; the new app gates the feature on `fwUpdateProto`.
- **Suppress duty-cycle sleep while a transfer is active** (transfer runs inside the BT task; verify
  no sleep transition can fire mid-transfer, and block `setRecordMode` during receive).
- **Implementation checkpoint:** confirm the `BluetoothSerial` RX buffer can hold one frame + slack at
  the chosen `chunkSize`; raise via `SerialBT.setRxBufferSize()` if needed (stop-and-wait means only
  one frame is ever in flight).
- Register commands in `BtCommands::initCommands()` alongside the existing `addCmd` list
  (`ElocCommands.cpp:626`).

**Verify:** native unit tests for the frame parser + CRC in `test/test_generic_*` (framework already
exists — `pio test -e generic_unit_tests`); on-hardware: scripted transfer over the robot/serial test
tooling (`tools/external_tests/`) or a throwaway Python SPP client; kill-connection-mid-transfer →
resume completes; wrong hash → apply refused.

## Phase 2 — Android app: transfer engine + MVP UI (file picker)

**Files:** new `driver/FirmwareUpdater.kt`; edits to `driver/DeviceDriver.kt`, `data/Command.kt`,
`driver/General.kt`; new `services/FirmwareUpdateService.kt`; new activity
`activities/themable/FirmwareUpdateActivity.kt` + layout; entry point in `DeviceSettingsActivity.kt`.

1. **`FirmwareUpdater` transfer engine** (object or class coordinated by `DeviceDriver` — keep the
   single-socket rule: all writes still go through `DeviceDriver`):
   - Pause the normal command queue (`processingCommandList` flag / stop `executor` polling) for the
     duration; also pause any periodic `getStatus` polling from the UI.
   - Send `setFwUpdateBegin` as a normal queued command; then stream frames on
     `bluetoothSocket.outputStream` directly, consuming acks via the existing `listenForData()`
     EOT-JSON loop (acks are ordinary responses — **no read-loop changes needed**; route them via a
     dedicated listener like the existing `onSetCommandCompleted` maps).
   - Per-frame ack timeout 10 s; on timeout/disconnect: reconnect (`DeviceDriver.connect`), issue
     `getFwUpdateStatus`, resume from `bytesReceived`.
   - Progress callback: bytes sent / total, rate, ETA.
2. **`FirmwareUpdateService`** — foreground service modeled on `StatusUploadService.kt`: persistent
   notification with progress, partial wake lock, survives screen-off. Terminal notification states:
   success / failed-rolled-back / resume-available.
3. **MVP UI (`FirmwareUpdateActivity`)** reachable from `DeviceSettingsActivity`:
   - Shows installed version (already parsed into `General.version` from `getStatus`
     `device/firmware`).
   - **File picker** (SAF) for a local `.bin`; app computes SHA-256 + size itself and displays them.
   - Preflight checklist rendered live from `getStatus` + `setFwUpdateBegin` error codes (recording
     on → one-tap stop offer; low battery / SD full → blocking message with the firmware-reported
     reason).
   - Transfer progress → "Applying — device will restart" → auto-reconnect loop (retry connect for
     ~2 min; device reboots twice: trigger-boot + flash + final boot) → `getStatus` → compare
     `device/firmware` to expected version → ✅ / ⚠️ terminal screen. Read
     `/sdcard/eloc/update/result.json`? No SD file access over BT exists — rely on version comparison
     + rollback state; if version unchanged after reconnect, report "failed, device rolled back".
   - Gate the whole feature on `fwUpdateProto` in `getStatus`; hide the menu item for old firmware.
4. **Variant guard:** refuse to send an `ei` binary to a `no-ai` device and vice versa (compare
   manifest/file metadata variant vs `buildVariant` from `getStatus`). For the MVP file picker, embed
   variant in the release filename convention (see Phase 3 tooling) and warn if undeterminable.

**Verify:** real hardware only (no BT test suite exists — per app CLAUDE.md). Full bench matrix:
happy path both variants; downgrade; BT drop mid-transfer + resume; corrupt file; update-while-recording
refused; low-battery refused; old-firmware device → feature hidden.

## Phase 3 — Distribution backend + full "update available" flow

**Files:** app `data/helpers/firebase/FirestoreHelper.kt` (+ small new model class), `HomeActivity.kt`
badge, `FirmwareUpdateActivity` "latest available" path, `data/util/Preferences.kt` (beta opt-in);
firmware repo: new `tools/make_release.py`.

1. **Firestore `firmware_releases` collection**, one doc per release:
   ```json
   {
     "version": "v2.4.0",            // must equal what new firmware reports in getStatus
     "channel": "stable" | "beta",
     "releaseNotes": "...",
     "date": <timestamp>,
     "variants": {
       "ei":    { "storagePath": "firmware/v2.4.0/firmware-ei.bin",    "sha256": "...", "size": N },
       "no-ai": { "storagePath": "firmware/v2.4.0/firmware-no-ai.bin", "sha256": "...", "size": N }
     }
   }
   ```
   Binaries in the existing Firebase Storage bucket under `firmware/`. Firestore rules: releases
   read-only to authenticated users; writes admin-only (manual console upload initially).
2. **Release tooling** in the firmware repo: `tools/make_release.py` — builds both envs (or takes
   `.pio/build/*/firmware.bin`), extracts the version string (same source as `genVersion.py` /
   `version.h`), computes SHA-256s, emits the manifest JSON and canonically-named files
   (`ELOC-<version>-<variant>.bin`).
3. **App flow:** on app start with connectivity, fetch latest manifest for the user's channel
   (`stable` default, `beta` if opted in via profile setting); download + cache the `.bin`s locally
   (verify sha256 after download); badge on `HomeActivity` device list; when connected to a device
   with older `device/firmware` + matching variant, show the "Update available" card in
   `DeviceActivity`/`DeviceSettingsActivity` → same Phase-2 preflight/transfer/apply/verify pipeline.
4. **Result upload:** after a completed (or rolled-back) update, queue a small result doc
   (device name/MAC — key on **mac_address**, not device_name — from/to version, outcome, timestamp)
   through the existing Firestore upload machinery (`FirestoreHelper` / `StatusUploadService`
   patterns) for fleet visibility on the web dashboard. Web-dashboard rendering is out of scope here.

## Sequencing for implementing agents

1. **Phase 0** — self-contained firmware fix; ship regardless. No app dependency.
2. **Phase 1 + Phase 2** — one coordinated firmware+app release (protocol versioned via
   `fwUpdateProto` from day one, so mismatched pairs degrade gracefully). The Phase-2 MVP (file
   picker) is the first user-visible deliverable.
3. **Phase 3** — backend + auto-discovery UX; pure addition on top.

## End-to-end verification (final acceptance, real hardware)

1. Flash a device with Phase-0/1 firmware version A. From the app, update to version B via file
   picker: preflight passes, transfer completes with progress, device reboots twice, app reconnects
   and shows "Updated to B", `getStatus` reports B.
2. Repeat with a **deliberately crashing** image → device auto-rolls back to A; app reports rollback.
3. Kill Bluetooth at 50% transfer → walk back, reopen app → resume completes from offset.
4. Attempt update while recording / with battery below threshold (bench PSU at 3.0 V LiFePo) / SD
   removed → firmware refuses with distinct error codes; app shows the reason.
5. Downgrade B → A succeeds.
6. Manual SD-swap update path still works (regression).
7. Phase 3: upload release via console; app on another phone discovers it, caches offline, updates a
   device with no internet present; result doc appears in Firestore.
