# Firmware version history

One line per firmware version — what changed and whether it was verified on hardware. This is the
quick index; the long-form analysis for each work stream lives in
[`memory-bank/changelog.md`](memory-bank/changelog.md) (finished work) and
[`memory-bank/activeContext.md`](memory-bank/activeContext.md) (work in flight).

**Convention:** every push bumps `VERSION` in [`include/project_config.h`](include/project_config.h)
by +0.01 **and** adds a line here, newest first. The version string is what the app shows and what
the OTA update flow compares, so a bump without an entry leaves a build nobody can identify later.

Status column: `HW` = verified on hardware, `build` = compiles and is reasoned through but not yet
bench-tested, `partial` = some paths tested (see the detail doc).

| V1.86 | 2026-11-19 | partial | **SD log no longer dies silently on exFAT; log files get real dates.** A deep sleep right after `eloc.log` grew into a new cluster left its FAT chain running through an undefined value, and from then on logging failed on every boot with no message while recording carried on. On hardware: 677/677 deep sleeps logged cleanly in a 678-wake duty-cycle run; the damaged-file path and the restart flush are not yet seen. Also: on-device test builds (`target_unit_selected_tests`) compile again. Details: `memory-bank/activeContext.md`. |
| V1.85 | 2026-11-19 | HW | **No more 64 ms audio hole every 65.5 s.** `I2S_DMA_BUFFER_LEN` 1024 → 512 and `I2S_DMA_BUFFER_COUNT` 8 → 16 (`project_config.h`; still 512 ms of buffering). 1024 × 4-byte frames exceeded the driver's 4092-byte DMA limit, IDF 4.4 clamped every buffer to 1023 frames, and one buffer was lost every 2^20 frames since I2S start: ~3.5 s per hour, the reason hourly WAV names stepped 3602-3605 s. Present since at least September (V1.74 logs); duty-cycle wakes under 65 s never hit it. Bench, ELOC_00190: 1123 s continuous recording, every rate window 15989-16007 Hz, no loss where the old buffers would have lost 17. Details: `memory-bank/progress.md`, Known Issues. |
| V1.84 | 2026-11-18 | partial | **Recording-only mode scales the CPU again (~27 → ~16 mA baseline), on a 100 Hz FreeRTOS tick.** `RECORDING_LOW_POWER` is min 10 / max 80 MHz again (20 at ≥ 30 kHz; `RECORDING_ONLY_DFS` in `project_config.h`), pinned at 80 since V1.59 because every frequency switch left `esp_timer` ~45 % and the tick ~25 % fast. The skew follows the switch rate, so `CONFIG_FREERTOS_HZ` is now **100 for every build**: +5.5 % / +3.2 % measured, the GPS wait ~28.5 s instead of 30. Audio, WAV length and file names are unaffected (APLL + RTC clock; 3600.000 s in a 60-minute file, next name 3601 s later). In recording-only mode at ≥ 16 kHz I2S now installs on the **APLL regardless of `MicUseAPLL`**, since on the PLL the driver pins APB at 80 MHz; AI modes keep the config value. **No change with LoRa enabled** (min = max as before). The Arduino core's 1000 Hz build check is switched off (`tools/skip_arduino_tick_check.py`), and waits that 100 Hz would have broken are fixed: RadioLib gets an exact `delay()` (`ElocRadioHal`; without it 4 of 6 joins failed with -5), the AI wait loops and the LoRa halt loop wait one tick, `main.cpp`'s `delay()` at least one tick, and the raw-tick waits in the LIS3DH start-up, battery averaging and log-file mutex are in ms now. **HW:** 75-min recording-only run (scaling, skew, file names) and an overnight `recordOn_detectOn` duty-cycle run with LoRa and APLL on (632 wakes: no reset, file names within ~2 s of GPS, OTAA joins, uplinks and downlinks all working, no 8× fault), both on the bench builds that this version makes standard. **Not yet on hardware:** this exact build, GPS sync while scaling, recording-only duty cycle, firmware update from the app, `esp32dev-tflm`. |
| V1.83 | 2026-11-17 | build | **Mic self-test verdict** (Phase 2 of `README-MicTest-Plan.md`). `getMicTest` now starts with `verdict`: `result` ok / broken / checkPort / suspect / repeat (none for a silent test), the deciding `finding` and a one-line `reason` for the user. The checks, in order, with limits from the 2026-11-17 bench sessions on ELOC_00247 (7 healthy mics, 2 broken, tissue and a thumb on the port, mic unplugged) and an hour of Sumatran forest noise mixed into them: no signal; beeps buried in noise (best tone's rise < 30 dB: broken); handling noise below 125 Hz or a pressed port (repeat); a loud background > -90 dBFS (repeat in a quiet place, never broken); a faint mic (best rise < 45 dB in a quiet background: broken); a blocked port (high tone > 18 dB below the low one: checkPort); crackle (>= 10 impulses and kurtosis >= 20: suspect); I2S clock > 5 % off (repeat). **A confirming second run** follows when the first finds anything (`confirm`, default 1): a fault counts only if both runs show it, so such a test takes ~24 s; the second run saves `_run2` files. PC: 34 mic-analyzer cases; the 9 bench mics, rebuilt from their numbers, get the right verdicts, and in the forest mix a healthy mic is never called broken (busy minutes `repeat`, the rest `ok` 99 %) while #6 and #7 are `broken` 100 %. Compiles; not yet run on a device. |
| V1.82 | 2026-11-17 | build | **Mic self-test corrected after the first bench test** (ELOC_00247, healthy unit; `README-MicTest-Plan.md` "Bench results"). Replaying its WAV through `MicAnalyzer.hpp` on the PC reproduced the device JSON to 0.1 dB. **The fading buzzer tone counted as crackle:** after switch-off the tone takes until ~240 ms after its mark to fade, but the analysis started at 200 ms, so the healthy mic showed 3 impulses (3 to 24 depending on the I2S read phase). The guard after switch-off is now 350 ms (`GUARD_OFF_MS`, 200 ms after switch-on unchanged) and the default gap 600 ms (range 400..3000). Replayed, the same recording gives 0 impulses, crest 13.3 dB and kurtosis 0.0 at every phase, and unchanged tone levels. **Default tones 2700/4000/5400 Hz** instead of 1000/2700/4000: the buzzer hardly produces 1 kHz (-79 dBFS, most of the sound in its 3 kHz harmonic, rise only 25 dB); 5400 Hz is inferred from the 2700 Hz tone's harmonic, not yet measured. The SD-card JSON gains an `analysis` section (guard times, parameters and every switch mark), so a saved WAV can be re-analysed exactly on a PC. The test now takes ~12 s instead of ~10 s. PC tests: 18 mic-analyzer cases, including the fading tail. Compiles; not yet run on a device. |
| V1.81 | 2026-11-13 | build | **Microphone self-test, raw numbers only (`setMicTest` / `getMicTest`)** — Phase 1 of `README-MicTest-Plan.md`, on branch `EDsteve/mic-test`. Field mics fail from ants and humidity as "only pink noise", "faint", "crackling" or dead; nothing mic-related left the device before. `setMicTest` plays buzzer tones (default 1000/2700/4000 Hz, twice) after 1.5 s of silence, captures the raw 24-bit samples before the gain shift into PSRAM, and analyses them afterwards: level, DC, clipping, stuck samples, an octave spectrum with its slope (pink ≈ 0, white ≈ +3 dB/oct), crackle count / crest / kurtosis / dropouts, and per tone how far the level rose with the buzzer on (median blocks on both sides, so crackles cannot fake or hide a rise). `getMicTest` returns progress, then the result. The capture is saved as a 24-bit WAV plus the result JSON in `/sdcard/mictest/`. **No pass/fail verdict yet**: the thresholds are to come from a bench session on real broken mics. Asynchronous like `getLinkCheck`; refused during a firmware transfer, a coverage survey or an intruder alarm; `setFwUpdateBegin` is refused while a test runs; no duty-cycle sleep while a test runs. New `I2SMEMSSampler::set_raw_tap()` and `ElocSystem::acquireBuzzerForTest()` / `testTone()` / `releaseBuzzerForTest()` (status beeps are dropped while held, knock guard stays engaged). The main loop also starts I2S when the test asks, so it stays the only owner of the driver; I2S is left running afterwards, as after a stopped recording. The analysis is header-only and unit-tested on the PC (`test_generic_mic_analyzer`, 16 cases). Nothing has run on hardware. Wiki not updated on purpose: the commands go in when the branch is merged. |

| V1.79 | 2026-09-24 | build | **New build `esp32dev-tflm`: AI detection on TensorFlow Lite Micro, with no Edge Impulse code** (Phase 1 of `README-TFLM-Runtime-Plan.md`). | V1.78 | 2026-09-11 | build | **The GPS is now held powered for a whole survey session.** `manageGpsWhileAwake()` had no survey case, so the burst manager powered the module off as soon as the first fix landed — ~40 s in — for `GPS_RESYNC_INTERVAL_S`. TinyGPS++ then latches: `location.isValid()` never goes false again, so every later point silently inherited the last-known position while still reporting `hasFix` true, collapsing a walked transect onto one spot. Confirmed in a field log: `GPS burst: fix acquired, powering GPS off for ~3600 s` at 51 s, then three consecutive CSV rows at an identical position, varying again only once a BT connection happened to re-power the module. V1.76 exempted survey mode from duty-cycle *sleep* for exactly this reason; the GPS burst path was missed, and both the wiki and the code comment already claimed the GPS ran continuously. Mirrors the BT-connected block (10 s init backoff; the still-powered module is adopted back by the burst logic on session end via the `powerOnUs==0` path). Placed after the intruder block so theft tracking keeps priority — moot today, since a running survey suppresses knock detection. **The survey CSV now logs UTC.** Column 0 is `utc` in ISO-8601 rather than device local time, whose offset could change *mid-session*: the GPS derives a zone from longitude (blind to DST, so an hour out for half the year across Europe) while the app's `setTime` pushes its own, last-writer-wins. One observed session held three clock regimes in 13 rows, with the timestamps running backwards. UTC also matches TTN's `received_at`, so the card and the server records can finally be joined by time and not only by frame counter — the app's `seconds` field was always an absolute epoch, so a phone-set clock logs correct UTC too. New trailing `clock` column (`gps`/`app`/`build`) marks rows written before anything had set the wall clock, whose timestamps are the firmware build date. `CSV_CLOCK` is appended last so pre-1.78 session files still re-export through `setSurveyExport`. **Web:** the coverage map converts UTC to the viewer's own zone (pre-1.78 `time` columns are shown as written rather than shifted a second time), and now reports uplinks that arrived with no GPS fix instead of rendering an empty map with no explanation. Wiki `LoRa-Signal-Survey` updated. Not yet bench-tested: the GPS fix needs a survey walked with the app **disconnected**. |

| V1.75 | 2026-09-11 | build | Survey fix, found on hardware: a session that never got a GPS fix transmitted at the interval floor **indefinitely**. `mSurveyHasAnchor` conflated "a sample has been sent" with "we have a position to measure distance from", and was only set inside `if (hasFix)` - so indoors, or under canopy before first fix, the due-check fired on every pass and the device sent every 10 s, emptying the 400/day budget in ~67 min on null-position points. Split into `mSurveyHasAnchor` (set unconditionally) and `mSurveyHasPosition` (gates the distance trigger); a fixless session now sends one anchor sample and falls back to the 10-minute idle backstop, and the first real fix triggers an immediate `firstfix` sample so the track anchors without waiting out the backstop. |
| V1.74 | 2026-09-02 | build | Intruder: a **candidate now sirens for 30 s and sends one LoRa message straight away**, so interference is reported even when it turns out to be an animal. Because the siren blinds the LIS3DH, the candidate's movement-listening window no longer starts until the siren and the knock guard are over — otherwise it would expire while the device was deaf and a real theft would be missed. The siren runs once per episode and is not restarted on promotion to CONFIRMED. New `intruderCfg.armDelayS` (default 300 s): knocks are ignored for this long after a recording/detection mode starts, and after boot, so setting a device up cannot trigger it. Knock detection is also suppressed while a coverage survey is running. `getStatus.intruder` gains `armsIn[s]` / `armDelay[s]`, and `armed` now reflects both. |
| V1.73 | 2026-09-02 | build | Intruder detection: knocks alone no longer raise an alarm. A knock burst opens a **candidate** (`IntruderState_t`); the accelerometer must then see real movement within `intruderCfg.confirmWindowS` for it to become **confirmed**, otherwise it expires having powered nothing on and sent nothing. Fixes the knock counter's off-by-one, so `thresholdCnt=5` now means six knocks, not seven. Alarm uplinks go out **only while moving**, immediately on movement resuming (no stale deadline), and never wait for a GPS fix. A stopped device transmits nothing on the alarm path; the heartbeat instead accelerates to `lorawan.alarmUpLinkIntervalS` (1 h) while latched, with the normal default lowered 24 h → 12 h. New timings `settleMs` / `confirmWindowS` / `quietS` / `alarmTimeoutH` (auto-clear, default 24 h); `intruderCfg.idleIntervalS` deprecated (parsed and reported, ignored). |
| V1.72 | 2026-09-01 | build | LoRa coverage survey ("signal strength mapper"): new `surveyCfg` config block and `ElocLora_survey.cpp`. Uplink-first - position uplinks carry no downlink and the map is built from TTN's gateway-side RSSI/SNR, with a LinkCheckReq only every Nth sample or on demand. Sampling triggers on **distance** with a per-SF duty-cycle time floor; adaptive SF ladder 7→9→10→12 driven by the link checks; ADR off and `setDutyCycle(true, 36000)` enforced for the session. GPIO0 forces an extra uplink, `getLinkCheck` (app) forces one with a downlink and beeps the 0-5 count readout. Every transmission is logged to `/sdcard/survey/*.csv` with its frame counter, so joining against Firestore turns a missing server record into a confirmed dead spot. KML + GPX are generated from the CSV at session close (and re-runnable over an older session), so a card pulled out of a finished survey opens straight in Locus Map or Avenza. New commands: `setSurveyMode`, `getSurveyStatus`, `getLinkCheck`, `setSurveyExport`. |
