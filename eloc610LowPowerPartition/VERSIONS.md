# Firmware version history

One line per firmware version — what changed and whether it was verified on hardware. This is the
quick index; the long-form analysis for each work stream lives in
[`memory-bank/changelog.md`](memory-bank/changelog.md) (finished work) and
[`memory-bank/activeContext.md`](memory-bank/activeContext.md) (work in flight).

**Convention:** every push bumps `VERSION` in [`include/project_config.h`](include/project_config.h)
by +0.01 **and** adds a line here, newest first. The version string is what the app shows and what
the OTA update flow compares, so a bump without an entry leaves a build nobody can identify later.

Status column: `HW` = verified on hardware, `build` = compiles and is reasoned through but not yet
bench-tested, `partial` = some paths tested (see the detail doc).

| V1.79 | 2026-09-24 | build | **New build `esp32dev-tflm`: AI detection on TensorFlow Lite Micro, with no Edge Impulse code** (Phase 1 of `README-TFLM-Runtime-Plan.md`). It runs the device model package that the web app's ELOC Model Training builds after every job, compiled in from `lib/eloc_ml/model/eloc_model_data.h`. Adds esp-tflite-micro v1.3.4 + ESP-NN v1.1.2 (unpatched), a C++ spec-v1 mel front-end on KissFFT, package validation at boot (a bad model leaves AI off with the reason in status `aiError`, never a crash) and a silence guard for a dead mic (`silentWindows`). Status `detection` gains `aiRuntime`/`aiModelId`/`aiModelCreated`/`aiLabels`/`aiModelDefaults`/`aiArenaUsed`/`aiLastMs`/`silentWindows`/`aiError`. The CSV is `EI-results-TFLM-<jobId>.csv`; `buildVariant` stays `"ei"`. **The EI build keeps its behaviour:** its per-window logic moved into `handleClassification()`, shared by both runtimes, with the same log lines, CSV and threshold; its only visible change is a new status key, `aiRuntime:"ei"`. The native tests build again (19/19) and the golden-vector inputs are bit-identical on the PC. The front-end's per-frame buffers take internal RAM only while 24 KB of it stays free (`ELOC_ML_INTERNAL_RESERVE`), then PSRAM: on the bench a 2 s / FFT 1024 model otherwise used all of it but ~1 KB, and every SD access failed with `ESP_ERR_NO_MEM`. Nothing is hardware-tested yet: next are `pio test -e target_tflm_tests` and the plan's acceptance list. |
| V1.78 | 2026-09-11 | build | **The GPS is now held powered for a whole survey session.** `manageGpsWhileAwake()` had no survey case, so the burst manager powered the module off as soon as the first fix landed — ~40 s in — for `GPS_RESYNC_INTERVAL_S`. TinyGPS++ then latches: `location.isValid()` never goes false again, so every later point silently inherited the last-known position while still reporting `hasFix` true, collapsing a walked transect onto one spot. Confirmed in a field log: `GPS burst: fix acquired, powering GPS off for ~3600 s` at 51 s, then three consecutive CSV rows at an identical position, varying again only once a BT connection happened to re-power the module. V1.76 exempted survey mode from duty-cycle *sleep* for exactly this reason; the GPS burst path was missed, and both the wiki and the code comment already claimed the GPS ran continuously. Mirrors the BT-connected block (10 s init backoff; the still-powered module is adopted back by the burst logic on session end via the `powerOnUs==0` path). Placed after the intruder block so theft tracking keeps priority — moot today, since a running survey suppresses knock detection. **The survey CSV now logs UTC.** Column 0 is `utc` in ISO-8601 rather than device local time, whose offset could change *mid-session*: the GPS derives a zone from longitude (blind to DST, so an hour out for half the year across Europe) while the app's `setTime` pushes its own, last-writer-wins. One observed session held three clock regimes in 13 rows, with the timestamps running backwards. UTC also matches TTN's `received_at`, so the card and the server records can finally be joined by time and not only by frame counter — the app's `seconds` field was always an absolute epoch, so a phone-set clock logs correct UTC too. New trailing `clock` column (`gps`/`app`/`build`) marks rows written before anything had set the wall clock, whose timestamps are the firmware build date. `CSV_CLOCK` is appended last so pre-1.78 session files still re-export through `setSurveyExport`. **Web:** the coverage map converts UTC to the viewer's own zone (pre-1.78 `time` columns are shown as written rather than shifted a second time), and now reports uplinks that arrived with no GPS fix instead of rendering an empty map with no explanation. Wiki `LoRa-Signal-Survey` updated. Not yet bench-tested: the GPS fix needs a survey walked with the app **disconnected**. |
| V1.77 | 2026-09-11 | build | Survey: defer a link check off the **first uplink of a freshly joined session**. Observed on hardware across two runs: fCnt 1 after a new OTAA join never gets a LinkCheckAns back while fCnt 2 does, with the gateway receiving fCnt 1 at a healthy RSSI (-89 dBm, SNR 10.25) - so it is not coverage. Requesting a check there made the survey beep "no link" next to a working gateway at the exact moment a ranger starts one. The check now carries over to the next uplink (a second or two later, no extra airtime). `mFreshSession` is set on NEW_SESSION in both `init()` and `attemptRejoin()`, cleared once an uplink has gone out. |
| V1.76 | 2026-09-11 | build | Duty-cycle deep sleep is suppressed while a coverage survey runs. `mSurveyActive` is RAM-only but `surveyCfg.enable` persists, so a timer wake did not resume a session - it started a **new** one with a new CSV file. With the shipped defaults (30 s awake / 120 s asleep, and `dutyCycle.enable` defaulting to **true**) a single walk fragmented into dozens of files with most of the survey spent asleep. Also corrected the wiki: recording and AI detection are **not** suspended during a survey, contrary to what the page claimed - only intruder detection is (V1.74) and now deep sleep. |
| V1.75 | 2026-09-11 | build | Survey fix, found on hardware: a session that never got a GPS fix transmitted at the interval floor **indefinitely**. `mSurveyHasAnchor` conflated "a sample has been sent" with "we have a position to measure distance from", and was only set inside `if (hasFix)` - so indoors, or under canopy before first fix, the due-check fired on every pass and the device sent every 10 s, emptying the 400/day budget in ~67 min on null-position points. Split into `mSurveyHasAnchor` (set unconditionally) and `mSurveyHasPosition` (gates the distance trigger); a fixless session now sends one anchor sample and falls back to the 10-minute idle backstop, and the first real fix triggers an immediate `firstfix` sample so the track anchors without waiting out the backstop. |
| V1.74 | 2026-09-02 | build | Intruder: a **candidate now sirens for 30 s and sends one LoRa message straight away**, so interference is reported even when it turns out to be an animal. Because the siren blinds the LIS3DH, the candidate's movement-listening window no longer starts until the siren and the knock guard are over — otherwise it would expire while the device was deaf and a real theft would be missed. The siren runs once per episode and is not restarted on promotion to CONFIRMED. New `intruderCfg.armDelayS` (default 300 s): knocks are ignored for this long after a recording/detection mode starts, and after boot, so setting a device up cannot trigger it. Knock detection is also suppressed while a coverage survey is running. `getStatus.intruder` gains `armsIn[s]` / `armDelay[s]`, and `armed` now reflects both. |
| V1.73 | 2026-09-02 | build | Intruder detection: knocks alone no longer raise an alarm. A knock burst opens a **candidate** (`IntruderState_t`); the accelerometer must then see real movement within `intruderCfg.confirmWindowS` for it to become **confirmed**, otherwise it expires having powered nothing on and sent nothing. Fixes the knock counter's off-by-one, so `thresholdCnt=5` now means six knocks, not seven. Alarm uplinks go out **only while moving**, immediately on movement resuming (no stale deadline), and never wait for a GPS fix. A stopped device transmits nothing on the alarm path; the heartbeat instead accelerates to `lorawan.alarmUpLinkIntervalS` (1 h) while latched, with the normal default lowered 24 h → 12 h. New timings `settleMs` / `confirmWindowS` / `quietS` / `alarmTimeoutH` (auto-clear, default 24 h); `intruderCfg.idleIntervalS` deprecated (parsed and reported, ignored). |
| V1.72 | 2026-09-01 | build | LoRa coverage survey ("signal strength mapper"): new `surveyCfg` config block and `ElocLora_survey.cpp`. Uplink-first - position uplinks carry no downlink and the map is built from TTN's gateway-side RSSI/SNR, with a LinkCheckReq only every Nth sample or on demand. Sampling triggers on **distance** with a per-SF duty-cycle time floor; adaptive SF ladder 7→9→10→12 driven by the link checks; ADR off and `setDutyCycle(true, 36000)` enforced for the session. GPIO0 forces an extra uplink, `getLinkCheck` (app) forces one with a downlink and beeps the 0-5 count readout. Every transmission is logged to `/sdcard/survey/*.csv` with its frame counter, so joining against Firestore turns a missing server record into a confirmed dead spot. KML + GPX are generated from the CSV at session close (and re-runnable over an older session), so a card pulled out of a finished survey opens straight in Locus Map or Avenza. New commands: `setSurveyMode`, `getSurveyStatus`, `getLinkCheck`, `setSurveyExport`. |
